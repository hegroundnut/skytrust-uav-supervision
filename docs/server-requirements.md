# SkyTrust 团队服务器资源需求文档

> 版本：2026-10-21 · 提交对象：团队服务器管理员
> 用途：申请**一台**可长期运行的服务器环境，承载 SkyTrust 全栈（四条联盟链节点 + 后端 + 前端，单机全栈形态）。
> 数据来源标注：**实测** = 生产部署机真实运行数据（`docs/version-matrix.md` §11/§12 逐条登记）；**◇估算** = 无实测登记、按同类组件推断，上线后需复测。

---

## §0 一页结论（申请规格）

| 项 | 最低可接受 | **推荐** |
|---|---|---|
| CPU | 8 核 | **16 核** |
| 内存 | 16 GB | **32 GB** |
| 磁盘 | 100 GB SSD | **200 GB SSD** |
| 操作系统 | Ubuntu 22.04 LTS | **Ubuntu 24.04 LTS**（现生产机实测同款） |
| 环境形态 | 见 §5——**必须是 VM / LXC 类完整系统**（systemd + sudo + cgroup v2 + 环境内可装 Docker） | 同左 |
| 入站网络 | SSH + 前端端口（15001/8090）对使用人可达 | 同左 |
| 出站网络 | 可访问 Docker Hub、hub-dev.cnbn.org.cn、goproxy.cn、github.com（或允许离线导入镜像/依赖） | 同左 |

一句话理由：现生产机 **2C/7.2G 实测已跑满四链全栈**，但稳态 load 1.38、风暴峰 load 8.3-11（实测登记），CPU 是唯一瓶颈；内存按各组件实测稳态 RSS 合计 9-12.5 GB + 内核 page cache 余量（IRITA 曾发生 cache 被挤干→leveldb refault 风暴→断链，实测教训）→ 16G 起、32G 稳。

## §1 这台服务器上会跑什么（负载清单）

单机全栈，共约 **30 个常驻进程/容器**，全部由本仓库 `scripts/*.sh` 编排（与现生产机完全同构）：

| 组件 | 数量 | 形态 | 说明 |
|---|---|---|---|
| ChainMaker 监管链节点（v2.3.10，TBFT） | 5（wx-org1..5） | 原生进程 | 共识持续运行 |
| ChainMaker 合约 VM 引擎（v2.3.9） | 5 | Docker 容器 | 每 org 一个，`--network host` |
| Fabric 运营链（test-network，SMARTBFT） | 4 orderer + 4 peer | Docker Compose | peer = 2 org × (peer0+peer1) |
| Fabric 链码容器（dev-peer*） | 4 | Docker 容器 | 每 peer 一个，单容器限额 150MB（实测登记） |
| FISCO BCOS 管理链节点（v3.16.4，PBFT） | 4 | 原生进程 | air 二进制 |
| IRITA 证照链节点（v4.0.0，Tendermint BFT） | 4 | 原生进程（systemd-run 限额单元） | **每节点 CPUQuota=30% + MemoryHigh=420M 红线限额**，出块 ~1.5s，空块 4-5 万/日 |
| skytrust-backend（Go，realchains 构建） | 1 | 原生进程 | 实测稳态 RSS 仅 43MB |
| 前端静态服务 + API 代理（python3） | 1 | 原生进程 | :15001 统一入口，负载可忽略 |
| cm_db（MySQL 5.7）＋ gchain 管理平台 | 各 1 | Docker 容器 + 原生 | **可选组件**（区块浏览器/管理面），核心验收不依赖 |

> 「每条链至少 4 节点」已满足：CM 5、Fabric 4+4、FISCO 4、IRITA 4。若未来 CM 缩到 4 org，总预算变化 <1GB，不影响本文结论。

## §2 内存预算（逐项，标注来源）

| 组件 | 单实例稳态 | 小计 | 来源 |
|---|---|---|---|
| CM 节点 ×5 | ~630-710 MB | **3.2-3.6 GB** | 实测：org1-4 同工作量稳态 RSS≈630MB；org5 移除 GOMEMLIMIT 后 710MB 定案（version-matrix §12.12——**450/650MiB 两档堆限均触发 GC thrashing**，86-100% CPU，故 CM 节点不设堆限是实测定案，不是疏漏） |
| CM VM 引擎 ×5 | ◇100-200 MB | **0.5-1.0 GB** | ◇估算（未单独登记） |
| Fabric peer ×4 | peer1 限额 350MB、稳态 253-291MB；peer0 未限额同量级 | **1.2-1.6 GB** | 实测（`run-peers-local.sh -m 350m` + RSS 曲线登记） |
| Fabric orderer ×4 | ◇100-250 MB | **0.4-1.0 GB** | ◇估算 |
| Fabric cc 容器 ×4 | 限额 150 MB | **0.6 GB** | 实测（core.yaml Memory=157286400） |
| FISCO 节点 ×4 | ◇100-300 MB | **0.4-1.2 GB** | ◇估算（C++ 节点，无登记） |
| IRITA 节点 ×4 | MemoryHigh 420M / GOMEMLIMIT 350MiB，稳态 ~293-350MB | **1.2-1.7 GB** | 实测（§12.12 限额定案 + cgroup memory.current 登记；最坏 +520MB 复核在案） |
| 后端 + 前端 | 43 MB + ~30 MB | **<0.1 GB** | 实测（后端 RSS 43MB 为两轮验收期间登记值） |
| cm_db + gchain（可选） | buffer-pool 64M → RSS ~300-400MB；gchain ~100-200MB | **~0.6 GB** | 限额实测，RSS ◇估算 |
| OS + dockerd + 杂项 | — | **0.8-1.2 GB** | ◇估算 |
| **进程小计** | | **≈9-12.5 GB** | |
| **内核 page cache 余量** | IRITA 断链事故的直接机理：物理内存贴顶 → page cache 被持续回收（memory.events high 16-21 万次）→ leveldb refault 风暴（累计读盘 81GB）→ 握手饿死 → 4 节点 mesh 断裂 | **≥4 GB** | 实测教训（§12.12） |

**结论：16 GB 是保住「实测限额配置 + cache 余量」的下限；32 GB 让 CM/Fabric 未限额组件和构建期（Go 编译、合约构建）都有从容空间。**
两条附带纪律：① 上线时**原样沿用**现有脚本里的限额值（它们是按稳态工作集校准过的实测定案）；② 若给到 32G 想放宽限额，必须按 §12.12 教训「部署后数小时复测 RSS/回收计数」再动——放宽通常安全，收紧绝不拍脑袋。

## §3 CPU 预算

| 负载 | 数值 | 来源 |
|---|---|---|
| IRITA 硬配额（红线） | 4 节点 × CPUQuota 30% = **1.2 核恒占上限** | 实测（`start-irita.sh`，用户红线：绝不无限额启动） |
| 全链稳态 | 2 核机整改后稳态 **load ≈1.38**（四链出块 + 后端 + VM 引擎） | 实测（§12.12 恢复实证） |
| 验收/演示风暴峰 | 整改后峰值 **load 8.3**（整改前曾 40-93） | 实测（§12.6 两轮验收登记） |
| GC 事故参考 | CM 堆限贴活堆时单节点烧 82-100% CPU、整机 load 11 | 实测（§12.12，已通过移除堆限根治） |
| 构建窗口 | 后端 CGO 构建（现生产机被迫 `GOFLAGS=-p=2 GOGC=50`）、5 个 docker-go 合约构建、IRITA 源码构建 | 实测约束（低配机的妥协参数，高配可放开） |

**结论：8 核 = 稳态 1.4 核 + 风暴峰 8.3 的实测口径下不再过载的底线；16 核 = 风暴期浏览器多门户演示、E2E 压测与链上出块互不拖累，且构建窗口从「分钟级排队」变「并行秒过」。** 现生产机 2 核的问题正是：任何一次风暴（load 8-11）都会把 IRITA /status 探活拖超时、把演示拖卡——这是本次申请的直接动因。

## §4 磁盘预算

| 项 | 占用 | 来源 |
|---|---|---|
| Docker 镜像（fabric peer/orderer/ccenv/ca + CM VM 引擎 + mysql + golang 构建镜像） | ~6-10 GB | ◇估算（按镜像清单） |
| 仓库 + 7 个子模块 + Go build cache + 链二进制构建产物 | ~10-15 GB | ◇估算 |
| 四链初始账本 + 证书物料 | ~5 GB（参考：CM 单 org 账本同步 186MB 实测） | 实测参考 |
| **持续增长项**：IRITA 空块 4-5 万块/日（create_empty_blocks=true，实测登记）+ 各链日志 | 数 GB/月量级 | 实测（§12.5 隔夜登记） |
| 历史事故参考 | 现生产机磁盘 96%、仅剩 4.3GB——主因之一即 `irita node*.log` 无轮转（单文件 172MB） | 实测（§12.12 遗留卫生项） |

**结论：100 GB 起步、200 GB SSD 推荐**；并要求：① 日志轮转作为部署必做项（logrotate 或脚本内建）；② 账本目录（`/opt/chains`、`/opt/fisco/nodes*`、`/opt/irita/net`、fabric volumes）纳入备份策略——**账本是验收证据，P6-R6 永不删除**。

## §5 环境形态硬要求（给管理员的关键一节）

我们需要的**不是**一个普通 Docker 容器，而是一台「像虚拟机一样完整」的环境（VM / LXC / 带 systemd 的特权容器均可）：

1. **systemd + sudo**（硬要求）：IRITA 节点必须经 `sudo systemd-run` 瞬态单元携带 `CPUQuota=30%`/`MemoryHigh=420M` 启动——这是实测事故（无保护时 GC 螺旋 + refault 风暴两次拖垮整机）后立下的运维红线，**绝不无限额启动**。普通容器没有 systemd，此机制失效。
2. **cgroup v2**（Ubuntu 22.04+ 默认）：上述限额与实测校准值依赖它。
3. **环境内可安装并运行 Docker Engine + Compose 插件**（硬要求）：Fabric 网络、CM 合约 VM 引擎 ×5、cm_db 本身就是容器负载（即「容器里跑 Docker」，需嵌套虚拟化/特权支持）。若管理员更愿意宿主机直挂 `docker.sock`，需接受容器与宿主同级、资源限额由宿主 cgroup 管理的运维模式（可谈，但我们默认申请环境内自治 Docker）。
4. **普通 Docker 容器的降级路径（不推荐，仅备用）**：若团队只能给纯容器，则需要 ① 特权 + systemd 作为 PID 1 的镜像；② 外层容器级 `--cpus`/`--memory` 由管理员设定；③ `start-irita.sh` 改造为环境内可用的限额机制（cgroup v2 委派手工建组），改造前红线语义（每 IRITA 节点 30% CPU 上限）必须等价保留——这部分是我们的工作量，但会引入未验证路径，故列为下策。
5. **持久化**：环境重启/重建不得清空数据盘——四链账本、证书物料、SQLite 业务库、SM9 密钥都在其上（详见 §4-②）。
6. **时钟**：NTP/chrony 同步 + 时区 `Asia/Shanghai`（BFT 共识与后端时间戳铁律都依赖）。

### 5.1 请管理员先回答的三个问题（决定给哪种形态）

1. 这个「容器」是 **VM / LXC 类完整系统**（有 systemd，`systemctl` 可用，我们是 root/sudo），还是**普通 Docker 容器**？
2. 环境内能否**安装并运行 Docker Engine**（嵌套）？若不能，可否挂载宿主 `docker.sock`？——注意：挂 sock 方案下 Fabric/VM 容器会成为宿主同级容器，与本环境的网络命名空间隔离（CM 节点连 `127.0.0.1:2235N`、后端连 `localhost:7051` 均跨命名空间失配），外层被迫 `--network host`，约 35 个链端口与宿主/其他租户同池冲突，且 sock 等价 root 权限——**共享服务器上不建议走这条路**。
3. 数据目录是否**持久化**（环境重建/重启不丢 `/opt` 类数据盘）？

三问全「是」→ 按本文其余章节交付即可，脚本零改造。任一「否」→ 见 5.2 底线。

### 5.2 若只能给普通 Docker 容器（诚实的范围底线）

- **仍可承载**：后端 **sim 模式**（纯 Go、零 Docker/Java/链依赖，`CHAIN_MODE=sim` 开箱即用）+ 前端三门户 + 全套 hermetic 测试（~315 项）——开发、演示、接口联调不受影响。
- **无法承载**：四链真实部署——Fabric 整网（12 容器）与 ChainMaker DOCKER_GO 合约 VM 引擎（5 容器）**强依赖 Docker 守护进程，属结构性阻塞**（CM 节点可启动但任何合约交易都执行不了）；IRITA 限额机制需按 §5-4 改造且属未实测路径。
- **结论**：本需求文档的验收目标（四链真实数据、`scripts/run-acceptance.sh` 五项）必须落在 §5 的 VM/LXC 形态上；普通容器只能作为开发/演示环境的补充，不能替代。

## §7 网络需求（单机全栈的红利：链端口零暴露）

- **入站**：仅需 ① SSH（使用人 IP）；② 前端端口 **15001**（生产统一入口）与 8090（备用）对使用人浏览器可达。四条链的全部端口（12301-12305/11301-11305/7050-7061/9051/9061/20200-20203/30300-30303/26656-26687+）、后端 :8080、cm_db :3306 **一律留在环境内部/回环，不对任何外部源开放**——包括 IRITA 无鉴权的 rpc。
- 因全栈同机，**无需 SSH 隧道、无需跨机端口放行、无需 IP 白名单维护**（此前 `docs/deployment.md` §4 跨机方案的最大痛点在单机形态下自然消失）。
- **出站**：Docker Hub（fabric/mysql/golang 镜像）、`hub-dev.cnbn.org.cn`（CM VM 引擎镜像）、`goproxy.cn`（Go 依赖）、github.com（子模块与 IRITA 源码核对）。如服务器为隔离网络，请提前告知，我们改走离线镜像导入（docker save/load + GOPROXY 私有缓存）。

## §8 历史实测参考（为什么 2C/7.2G 不够）

| 机器 | 规格 | 承载 | 结局 |
|---|---|---|---|
| 老生产机 121.41.54.226 | 2C / 1.7GB + 2GB swap | 三链 + 后端（极限限额调优） | 可跑（实测），gchain 需借 swap；已于 2026-10-18 退役「只停不删」 |
| 现生产机 47.97.154.110 | 2C / 7.2GB | 四链全栈 + CM org5 + peer1×2 扩容 | 全栈跑通（实测），但 CPU 饥饿：风暴峰 load 8.3-11、IRITA 探活被拖超时、演示卡顿、构建被迫 `-p=2 GOGC=50`——**本次申请动因** |

即：**内存 7.2G 靠实测限额体系勉强够，CPU 2 核是结构性不足。** 8C/16G 消除结构性瓶颈，16C/32G 让验收风暴、多门户演示与构建窗口互不干扰。
